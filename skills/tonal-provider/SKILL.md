# Tonal Provider Skill

This skill covers Athlytics's Tonal integration: `core/providers/tonal_client.py` (`TonalClient`, low-level auth/HTTP), `core/providers/tonal.py` (`TonalProvider`, the `Provider`-protocol-conforming wrapper), and the 7 Tonal MCP tools (`mcp_server/server.py`).

There is no official Tonal API. Everything here is reverse-engineered, cross-verified against two independent open-source efforts (`dlwiest/ts-tonal-client`, `danmarai/tonal-api`) — see `docs/superpowers/specs/2026-08-24-tonal-integration-design.md` for provenance and confidence notes.

## How it works

- Tonal has no OAuth app registration — auth is a direct Auth0 resource-owner password grant against `https://tonal.auth0.com`. The connect flow (`app/data_sources.py`'s `connect_tonal`) takes a raw email/password from the athlete, not a redirect flow like Strava's. Credentials live in their own encrypted `CredentialStore` at `/data/tonal_credentials.enc`, separate from Garmin's and Strava's.
- `TonalClient.__init__` reauths only if its stored token is missing or within `TOKEN_EXPIRY_BUFFER_SECONDS` (60s) of expiry; every `_get`/`_post`/`_delete` call also calls `_ensure_fresh_token()` first and retries once on a 401. `_reauth` tries a refresh-token grant first (cheap, no password sent) and falls back to a full password login only if that fails — mirrors both upstream reference clients.
- `get_movements()` caches the full movement library in-memory on the `TonalClient` instance with a 24-hour TTL (`MOVEMENTS_CACHE_TTL_SECONDS`), per-instance rather than a disk file — same convention as `StravaProvider`'s per-instance activities cache. `search_movements()`, `estimate_workout()`, and `create_workout()` all go through this cache; pass `force_refresh=True` to `get_movements()` to bypass it. **Caveat:** each of the 7 Tonal MCP tools in `mcp_server/server.py` currently constructs a fresh `TonalProvider`/`TonalClient` per call, so in practice this cache never survives across separate tool invocations — an `estimate_tonal_workout` immediately followed by `create_tonal_workout` re-fetches the full movement catalog twice. The 24h TTL is real and correct at the class level; it just isn't meaningful in the current MCP deployment shape. A module-level cached client in `mcp_server/server.py` would fix this — flagged as a known follow-up, not yet implemented.
- Workout writes (`estimate_workout`/`create_workout`) go through `expand_blocks(blocks, movement_map)` (pure function, no I/O, fully unit-testable) — it turns a list of exercise blocks/supersets into Tonal's flat per-set wire format: block/round numbering, superset ordering via `setGroup`, and rep-vs-duration dispatch based on each movement's `countReps` flag (alternating movements get reps doubled, matching Tonal's own display convention). It raises `ValueError` naming any `movement_id` not found in the movement map — never silently drops or passes through an invalid id.
- The real workout-history endpoint is `GET /users/{user_id}/workout-activities`, **not** `/activities`. The plan originally assumed `/activities`; live testing against a real Tonal account found that path always returns an empty list, so `TonalClient.get_activities` was written against `/workout-activities` instead. If you're extending this client and reach for `/activities`, don't — it looks plausible but is dead.
- Tonal's workout records carry no per-workout title field. `TonalClient.get_activities` synthesizes one client-side from `workoutType` (e.g. `"Strength Workout"`, falling back to a bare `"Workout"` if `workoutType` is absent) — don't expect a real athlete-authored title to come back from the API.
- A `strength-scores/distribution` endpoint was captured as a fixture (`tests/fixtures/tonal/strength_scores_distribution.json`) during the human fixture-capture checkpoint, but it is **not wired into `TonalClient` or `TonalProvider`** — no method calls it. Treat its existence and shape as unconfirmed/best-effort; if a future feature needs it, verify the response shape against a live account before relying on it, the same way the rest of this client's endpoints were verified.
- `get_muscle_readiness()` omits muscles absent from the raw `/muscle-readiness/current` response rather than defaulting them to 0 — this lets callers distinguish "no data for this muscle" from "readiness score is 0." `TonalProvider._fetch_readiness` reflects that: if the requested muscle isn't in the response, it returns no reading at all for that sync pass, not a zero.
- Readiness is snapshot-only: `TonalProvider._fetch_readiness` always returns a single reading timestamped "now," regardless of the `(start, end)` range `fetch()` was called with — the underlying endpoint has no historical range support. Strength score and the two workout-derived metrics (`tonal_workout_volume`, `tonal_workout_duration`) do backfill properly within a date range, filtered client-side since `get_activities`/`get_strength_score_history` only accept a `limit`, not a date range.
- `TonalProvider.get_workout_detail(conn, activity_id)` has a side effect beyond returning data: it persists the workout's per-set breakdown into the `strength_set` table (`core/storage/repository.upsert_strength_sets`), keyed as `f"tonal:{activity_id}:{set_index}"`. `get_movement_history` (see below) is the MCP tool that queries `strength_set` back out by movement — call it instead of fetching workout details one at a time to build per-movement history.

## Debugging a failed sync

1. Check `GET /api/sync-status` — a `"tonal"` key appears when Tonal is connected, source-keyed independently from Garmin/Strava (same `sync_run_status`/`sync_metric_status` tables, per `app/db.py`).
2. **Auth token rejected** — surfaces as `TonalAuthError` (raised when both the refresh-token grant and the password-login fallback fail in `_reauth`). This means the athlete's Tonal password changed or the refresh token was revoked; there's no MFA/relogin-prompt flow like Garmin's — the fix is reconnecting via the onboarding Connect step or Settings with the current password. Not retryable with backoff, unlike a rate limit.
3. **Invalid movement ID on a write call** — `expand_blocks` raises `ValueError: unknown Tonal movement id(s): ...` before any HTTP write happens. First check whether the movement cache is stale: `get_movements()` only re-fetches after its 24h TTL expires, so a movement added to Tonal's library very recently, or an id typo'd by the caller, are the two likely causes — not a data corruption issue. Call `search_tonal_movements()` (or `get_movements(force_refresh=True)` at the client layer) to confirm the id is real and current.
4. A `401` mid-sync that isn't a full auth failure is handled transparently — `TonalClient._get/_post/_delete` retry once after reauth — so if you see repeated 401s in logs beyond that single retry, suspect Auth0 rate-limiting or lockout from repeated failed logins rather than a normal expiry. Be conservative here: don't retry password auth in a loop.

## Using the MCP tools

Read tools:
- `sync_tonal_data(days: int = 30, force_full_history: bool = False)` — same shape as `sync_garmin_data`/`sync_strava_data`: incremental by default (resumes from each metric_type's checkpoint), `days` only matters on first sync. `force_full_history=True` is for a deliberate one-off resync only. **Updated:** incremental runs (non-`force_full_history`) now also hydrate `strength_set` and `strength_set_muscle_group` tables via a `"tonal_strength_sets"` checkpoint, capturing per-set reps/weight/volume from recent workouts without requiring a manual `get_tonal_workout_detail` call on each. When `force_full_history=True`, this checkpoint is explicitly skipped and left untouched, to allow independent full resyncs of workout history.
- `search_tonal_movements(query: str | None = None, muscle_group: str | None = None)` — searches the cached movement library by keyword and/or exact muscle group (e.g. `"Chest"`, `"Quads"`).
- `get_tonal_workout_history(limit: int = 10)` — most-recent-first list of past workouts, each with an `activity_id` usable with `get_tonal_workout_detail`. This tool talks to `TonalClient` directly rather than through `TonalProvider.fetch_activities`, specifically to preserve `total_volume_lbs` — the `Activity` dataclass `fetch_activities` maps into has no such field and would silently drop it. **Updated:** returned dicts now include `planned_sets`, `completed_sets`, and `completion_rate` (fraction of sets with `repCount > 0` or `duration > 0`); see `docs/superpowers/specs/2026-08-24-tonal-integration-design.md` §Heuristic for "completed" set definitions. The heuristic can slightly undercount on certain bodyweight-style movements (e.g., assisted or assisted-chain variations where set completion is recorded differently).
- `get_tonal_workout_detail(activity_id: str)` — per-set breakdown (reps, weight, volume, one-rep-max) for one workout; also persists those sets into `strength_set` as a side effect (see above).
- `get_movement_history(query: str, limit: int = 20)` — local-data-only tool; searches `strength_set` table for sets matching a movement query string (case-insensitive substring match on movement name). Returns chronological per-set details (date, reps, weight_lbs, one_rep_max, volume_lbs, is_warm_up, struggling_score) for a single movement over the lifetime of available strength-set data. No live Tonal API calls — reflects only data already hydrated by prior `sync_tonal_data` runs.
- `get_muscle_group_volume(start_date: str, end_date: str)` — local-data-only tool; aggregates total volume (reps × weight) by muscle group over a date range (ISO 8601 format, e.g. `"2026-08-01"`) from the `strength_set_muscle_group` table. No live Tonal API calls — only reflects strength sets already persisted by `sync_tonal_data` incremental runs or manual `get_tonal_workout_detail` calls.

Write tools — **always call `estimate_tonal_workout` before `create_tonal_workout`, and get the athlete's confirmation on the estimate first.** This is a documentation/prompt-level convention, not a code-level gate: a bad `create_tonal_workout` call pushes a real workout onto the athlete's physical Tonal machine, not just a database row.
- `estimate_tonal_workout(blocks: list[dict])` — no side effects on Tonal's end, safe to call freely; validates every `movement_id` via `expand_blocks` and returns estimated duration + set count.
- `create_tonal_workout(title: str, blocks: list[dict])` — pushes the workout to the machine. Only call after the athlete has confirmed the estimate.
- `delete_tonal_workout(workout_id: str)` — deletes a workout by id.

`blocks` shape for the two write tools: a list of `{"exercises": [...]}` blocks (supersets share a block), each exercise a dict with `movement_id` plus optional `sets`, `reps`/`duration`, `weight_percentage`, `burnout`/`spotter`/`eccentric`/`chains`/`warmUp`/`dropSet` flags — see `expand_blocks` in `core/providers/tonal_client.py` for the exact field defaults.
